# RAG 知识库原理（小白快速入门）

> 一句话看懂：**RAG = 先从你自己的资料里"翻书"找到相关片段，再让大模型"照着片段"回答，并标出出处。**

---

## 1. 为什么需要 RAG？

大模型（DeepSeek、Qwen 等）很聪明，但有两个"先天缺陷"：

1. **它不知道你公司的私有资料** —— 你的芯片 SDK 源码、开发指南、原理图，它训练时根本没看过。
2. **它会一本正经地胡说八道（"幻觉"）** —— 你问它没学过的东西，它可能编一个看起来很专业的错误答案。

RAG（**R**etrieval-**A**ugmented **G**eneration，检索增强生成）就是解决这两点的：

> **不让大模型"闭卷考试"，而是"开卷考试"** —— 先在你的资料库里翻到相关段落，把这些段落塞进提示词，让大模型"照着资料回答，没资料就明说不知道"。

这样答案**有据可查**（带引用来源），也**不会瞎编**（只基于你给的资料）。

---

## 2. 整体流程：两条线

RAG 系统分成两件事，就像"图书馆"要先"上架"，才能"借阅"：

```
【一、入库（Ingestion）—— 把资料上架】
  文件（PDF / Word / Markdown / 源代码 / 原理图）
      │  ① 解析 loader：转成纯文本，记下来源 + 页码
      ▼
  纯文本
      │  ② 分块 chunker：长文本切成小块
      ▼
  文本块 chunk（每块带 来源 / 页码 / 序号）
      │  ③ 向量化 embedding：每块 → 一串数字"向量"
      ▼
  向量库 vector store（SQLite 存 向量 + 原文 + 元信息）

【二、问答（Query）—— 借阅 + 答题】
  用户提问
      │  ④ 问题也用同一套 embedding 向量化
      ▼
  ⑤ 检索 retriever（混合：向量相似度 + 关键词 BM25）
      │
      ▼
  最相关的 top-K 个文本块
      │  ⑥ 拼进提示词，让 LLM 照着资料回答，标 [n] 引用
      ▼
  答案 + 引用来源（哪个文件、第几页）
```

---

## 3. 入库：把资料变成"可检索"

### ① 解析（loaders）

不同格式用不同"解析器"，统一输出成**纯文本**，并记录元信息：

| 格式 | 解析器 | 说明 |
|---|---|---|
| PDF | `loaders/pdf.py` | 抽取文字 + 页码 |
| Word | `loaders/docx.py` | 抽取文字 |
| Markdown | `loaders/markdown.py` | 保留标题结构 |
| 源代码（.c/.h/.py…） | `loaders/code.py` | 整文件读取，标记 `kind=code` |
| 原理图 PDF | `loaders/schematic.py` | 图片多、文字少时，交给 VLM（视觉大模型）"看图说话" |

### ② 分块（chunking）

大模型一次能看的字数有限（上下文窗口），一整本书塞不进去，所以要切块：

- **普通文本**：`RecursiveCharacterSplitter`，默认 **800 字/块、前后重叠 100 字**（重叠是为了避免一句话被拦腰截断）。
- **源代码**：`CodeSplitter`，默认 **1500 字/块**，尽量让一个函数 / 结构体 / 宏定义不被拆散。

每块都会记下 `来源文件 + 页码 + 块序号`，并生成唯一 ID（哈希）—— 这就是后面"引用出处"的基础。

### ③ 向量化（embedding）—— 最核心的概念

计算机不懂"意思"，只会算数字。Embedding 模型把一段文字变成**一串固定长度的数字（向量）**，规则是：

> **意思越接近的文本，向量在"空间"里离得越近。**

示意（数字是假的，只为帮助理解）：

- "最大发射功率是多少" → `[0.12, -0.03, 0.88, ...]`（1024 个数字）
- "TX output power +11dBm" → `[0.11, -0.01, 0.85, ...]`（距离很近 ✅ 语义相关）
- "GPIO 上拉电阻" → `[0.71, 0.52, -0.20, ...]`（距离很远 ❌ 不相关）

于是"找相关片段"就变成了"算向量距离"（通常用**余弦相似度 cosine**，越接近 1 越像）。好的 embedding 模型还能做到**跨语言**——中文提问能匹配到英文资料（本项目实测：`qwen3.7-text-embedding` 支持中英跨语言检索）。

### ④ 存库（vector store）

把"向量 + 原文 + 元信息"一起存进 **SQLite**（本地单文件数据库，无需额外装向量数据库服务）。同时维护一份**关键词索引**，供 BM25 使用。

---

## 4. 问答：检索 + 生成

### ⑤ 检索（retriever）—— 混合检索

只靠向量有时会漏 —— 比如 `AB5766C`、`GPIO_PB9` 这种**精确词 / 型号名**，向量语义匹配可能不够准，但关键词匹配一抓一个准。所以本项目用**混合检索**：

- **向量检索**：算"问题向量"和"所有块向量"的相似度，取语义最像的 top-N。
- **BM25 关键词检索**：传统搜索引擎算法，按"词出现频率"打分，精确词匹配强。
- **RRF 融合**：把两份排名按名次加权合并（`1 / (k + 名次)`），得到一个综合排名，取前 top-K。

> 简单说：**向量负责"意思像"，BM25 负责"词对得上"，两者取并集再综合排序**，比单用一种更稳。

### ⑥ 生成（带引用）

把检索到的 top-K 个片段拼成"资料片段"，连同系统提示词一起交给大模型：

> "你是芯片原厂技术资料助手。请只依据提供的资料片段回答问题，并在回答中用 [1]、[2] 标注引用。如果资料中没有相关信息，就回答『资料中未找到相关内容』，不要编造。"

大模型"照着资料"作答，系统最后把答案里**真正引用到的那些 `[n]`** 挑出来（不是把所有检索候选都堆上去），返回**答案 + 引用来源（哪个文件、第几页）**。

## 5. 关键术语速查表

| 术语 | 大白话 |
|---|---|
| RAG | 检索增强生成：先翻资料再回答 |
| chunk / 文本块 | 把长文档切出来的小段 |
| embedding / 向量 | 文字变成的一串数字，意思相近则数字也相近 |
| vector store / 向量库 | 存向量和原文的地方（本项目是 SQLite） |
| cosine 相似度 | 两个向量"有多像"的度量（越接近 1 越像） |
| retriever / 检索 | 从库里找最相关的片段 |
| BM25 | 关键词打分算法（精确词匹配强） |
| RRF | 把多路检索结果按名次融合的算法 |
| top-K | 检索时取前 K 个结果（可配置 `RAGKB_RETRIEVAL_TOP_K`） |
| prompt / 提示词 | 你给大模型的"指令 + 资料" |
| citation / 引用 | 答案里标注的出处 [n]，对应到文件 + 页码 |
| provider / 适配器 | 可插拔的"外接服务"接口（LLM / Embedding / VLM） |

## 6. 本项目怎么对应

| 概念 | 代码位置 |
|---|---|
| 解析器 | `packages/ragkb/loaders/` |
| 分块 | `packages/ragkb/chunking/` |
| Embedding / LLM / VLM 适配器 | `packages/ragkb/providers/`（OpenAI 兼容 + 本地 BGE + fake 离线） |
| 向量库 | `packages/ragkb/indexing/sqlite_store.py` |
| 检索（混合 RRF） | `packages/ragkb/retrieval/hybrid.py` |
| 问答管线 | `packages/ragkb/core/rag.py` |
| 摄入管线 | `packages/ragkb/core/ingestion.py` |
| 配置 | `packages/ragkb/config.py`（环境变量 `RAGKB_` 前缀 / `.env`） |
| API / CLI | `apps/api/`、`apps/cli/` |

---

## 7. 一句话总结

> **入库**：文件 → 解析 → 分块 → 向量化 → 存 SQLite；
> **问答**：问题 → 向量化 → 混合检索（向量 + BM25 + RRF）→ 把片段喂给 LLM → 带引用的答案。
